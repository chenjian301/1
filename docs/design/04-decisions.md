## #1 怪与掉落：**全服共享**，奖励按**伤害最高的玩家**结算

**决定**：怪是**全服共享实体**（同一只怪、同一份血量）；击杀后**奖励（经验 + 宝箱）归"对该怪累计伤害最高"的玩家**。

**据此必须改动的架构（这条推翻了我原来的"每人一份"方案）**：

| 原设计 | 改成 |
|---|---|
| 怪由客户端本地模拟 | **怪由服务端权威模拟**：位置、血量、AI、重生、归属全在服务端 |
| 客户端算伤害、客户端算掉落 | 客户端只发**攻击意图**；伤害、血量、掉落、归属由服务端裁决（客户端仅做表现预测） |
| `snap{players[], guildAnchors[]}` | `snap{players[], monsters[], guildAnchors[]}` —— **怪也要走 AOI 广播**（不然看不见别人的怪） |
| "没人订阅的区块不模拟" | 仍成立，但**有玩家的区块必须跑怪 AI** → 服务端 CPU 随在线人数增长 |

**代价（你要知道的事）**：

1. **抢怪是设计内的行为**：你正在打的怪，会被路过的强者一刀抢走奖励（规则只看"累计伤害最高"）。自动战斗下这非常直观。若日后要缓解，有两个现成补丁：① **首击保护**（首先攻击者独占 N 秒）；② **伤害门槛**（造成 ≥ X% 血量伤害才有资格分奖励）。**首版按你的决定实现、不做保护**，但代码里留好这两个开关的位置。
2. **服务端成本上升**：这是"做真 MMO"的必然代价；控制手段是**每区块怪密度上限 + 分帧 tick**（把怪分散到不同帧计算，避免单帧尖峰）。
3. **延迟表现**：怪的血条会有 100~200 ms 的滞后，用客户端数值预测来缓解。

## #4 数值：号角 **500 金币**，20 级约 **15 分钟**

**决定**：号角 = 500 金币；1 级 → 20 级约 15 分钟。

**据此要做的改动（原草案数值差了一个数量级，全部作废重算）**：

- 原草案（20 级 25~40 分钟、号角 50,000 金币）→ **废弃**。
- 新目标：**T20 = 15 分钟 = 900 秒**。按"自动战斗 1.6 次/秒、普通怪 3~5 刀死"估算 → 约 **2.5 秒/只** → 15 分钟约 **350 只怪**。
- 由此反推：`1~19 级所需经验总和 ÷ 350 ≈ 单怪平均经验`。
  取 `need(L) = 150 × L^1.5`（1→20 累计约 10 万经验）→ **单怪经验需 ≈ 290**（原草案"8 × 怪等级"只有 8~24，差 20 倍）。
  → 改为 `经验 = 120 + 怪等级 × 60`（band 0 的 1~3 级怪 = 180~300），精英 ×5。
- 金币同理：要让 500 金币"十几分钟内买得起" → `金币 = 4 + 怪等级 × 3`（band 0 每只 7~13）→ **约 50 只怪 / 2 分钟就够**。
  → ⚠️ **这是我唯一建议你再想一下的数字**：这么便宜意味着"开服当天公会就会被建满"，公会失去稀缺感。若想让它珍贵一点，`3,000~10,000 金币`（15~50 分钟）更合适。
- ⚠️ 以上全部是**估算**：必须在阶段 A 实机跑一次，用**实测"秒/只"**反算才算校准完成（文档 01 §13 保留参数化形式，不写死数字）。

## #7 端：**只做小游戏端**

**决定**：只做抖音小游戏，不做 H5 发行版。

**据此**：`src\platform\` 只实现 `douyin.ts`，**不写 `web.ts`**。

⚠️ **必须说清的风险与我的替代方案**：不写 web 端 = 失去"浏览器端到端 harness"这条自动化验证通道，而上一版正是靠它在发布前抓到"静态检查全过、一进游戏就白屏"的致命错误。替代方案如下（**不需要写 web 端也能拿回大部分价值**）：

1. **逻辑层做成纯函数、与画布和平台完全无关** —— `core/ world/ game/` 里**禁止**出现 `document` / `canvas` / `tt.` / `window`；
2. 于是可以在**云服务器的 node 里直接跑无头断言测试**（`tools\test-logic.mjs`，不需要浏览器、不需要 DOM）：地图确定性（同坐标必同结果）、自动选目标、伤害与归属结算、掉箱概率分布、等级曲线、公会规则、AOI 订阅集合 —— **这些恰恰是最容易错、也最值得断言的部分**；
3. 渲染与手感只能靠**抖音 IDE 模拟器 + 真机预览**（人工），但会配一个**自绘调试面板**（F1 呼出：FPS、实体数、已加载 chunk、当前目标、伤害日志、地图种子），让"人眼验收"也有据可依。

**结论：只要逻辑层保持纯净，"只做小游戏端"与"可自动化验证"并不矛盾。** 这条会写进 `check-minigame.ps1` 的静态红线。

- **验证**：断言 183 → **226**（新增 `checkMap` / `checkLook` 两组：营地几何与道具合法性、路网确定性、

  这一条立刻抓到一处真问题：石砖地一开始用 48px 砖，**光这一项就 550 次落笔/帧**，改成 96px 后降到 ~65。

## #12 阶段 A6 落地记录（2026-09-30：装备目录与外观 + 属性系统 + 营地安全区 + Q版与视角 + UI 图标）

**背景**：用户这次提了一整批需求 ——
"宝箱可以开出来装备，给各个等阶的装备都各自添加十件，装备穿戴后会添加到人物外观（穿武器人物外观的武器会变），
每一件武器/衣服/鞋子都对应装备外观与装备内观（背包显示）；所有装备类型分为武器、衣服、鞋子、饰品；
所有装备都有等级划分，需要满足对应等级才能穿戴，还有属性添加 —— 给人物添加属性系统。
营地不刷新怪物；把地图和人物都做得更加细致，需要扩大视角分辨率，做 Q版可爱的人物和更细致的地图、UI；
每个 UI 按钮都做出对应的图标；登录注册页面按钮上没有显示对应操作的文字，待修复。"

**落地内容**

- **装备目录 60 件**（`shared\balance.json` 的 `equipment.catalog`；六阶**各 10 件**：武器 3 / 衣服 3 /
  鞋 2 / 饰品 2）：每件写死 `名字 + 部位 + 外观字段 + 阶内序号`。`09-equipment.generate` 从**该阶的 10 件里
  抽一件**再抽词条 —— 于是每件都有名字（"龙牙巨剑"）、有造型、有自己的等级门槛，而不是"随机一个部位"。
- **四个部位**：武器 / 衣服 / 鞋子 / 饰品（原来 6 个部位里的头盔与手套并入衣服）。
  主属性按部位分工：攻击 / 生命 / 防御 / **暴击率**（饰品）。
- **等级门槛（"装备的等级划分"）**：`1 + (阶-1)×3 + floor(阶内序号/4)` → 1 阶 Lv.1~3、6 阶 Lv.16~18
  （目标满级 20，所以最高那件也穿得上）。`EQUIP.canWear` 是**唯一闸门**：开箱的自动穿上与手动点都会先过它
  （穿不上就只进背包 / 提示差几级）。
- **同阶内越靠后越强**：`statMul = 1 + 阶内序号 × 0.02`（第 10 件 +18%）—— 同阶里也有"更好的那一件"。

## #14 阶段 A7 的修订（2026-09-30：摇杆让开底栏 + 地表细到 16×16 + 打全地图最近的怪）

三条都是用户当场反馈后改的（玩家可见的规则见 `01-game-design.md` §18）。只动了两处数值
（`world.tileSize`、`combat.targetRange`），其余改的是**几何口径**与**选目标口径**。

**做了什么**

| # | 改动 | 落地位置 |
|---|---|---|
| 1 | 摇杆触发区的**下边 = 整条吸底动作栏的顶边**（左边起 `zoneWidthRatio` 宽、从这条线往上 `zoneHeightRatio` 高） | 15-input 新增 `zoneBottom()`（读 17-hud `bottomBarTop()`，拿不到 HUD 时退化成屏幕底）+ `stickZone()` 改用它；`inStickZone()` 不用改。自检与 `tools\hud-preview.mjs` 画的框读的都是 `stickZone()`（只有一处几何） |
| 2 | 地表网格 8×8（渲染里原本写死 5×5）→ **16×16**；色档 3 → **6**（3 种结构色 × 亮 / 暗 2 档）；细纹 12 → **40 道/chunk** | `shared\balance.json` `world.tileSize` 64 → 32（带 `_tileSize` 说明，明确写"只影响渲染、不影响世界指纹"）；16-render `drawGround` 重写：按 `TERRAIN.tileCountPerChunk()` 遍历，**同一档色在同一行攒成一条 `ctx.rect` 路径再一次 fill**，最暗档与底色合并；导出 `groundLevel()` 给自检 |
| 3 | 选目标从"视野内最近"改成**已装载的全部怪里最近** | 07-combat 新增 `targetRange()`（0 = 不限）；`combat.visionRange`（540）→ **`combat.targetRange`（0）**；13-screen / 14-world / 20-main 里对视野半径的引用全部删掉（`pickTarget` 只认 `targetRange`） |

**四条关键取舍**

| # | 取舍 | 理由与代价 |
|---|---|---|
| a | 摇杆区的下边**吸在底栏顶边**，而不是"再缩小摇杆区宽度"或"把按钮挪高" | 用户的原话是"压住底下的按钮"。吸顶边是**几何上零重叠**的唯一做法：自检直接断言"功能键一个都不在摇杆区里"、`zone.bottom <= HUD.expTop()`；代价是摇杆区整体上移（设计稿 720×1600 上：下边从 1600 抬到 **1304**，整条底栏那一段不再算摇杆区），手指落点很低时第一下会没反应 —— 要调就改 `input.zoneHeightRatio`（0.68 是"从底栏顶边往上"的那一段） |
| b | `zoneWidthRatio` 保持 **1**（整条左半屏都是起手区） | 下边让开之后宽度不必再保守：屏幕左半边任何空白处都能直接起手走位，不用先摸左下角。代价是摇杆区与功能图标行**横向仍然重叠 667 CSS px** —— 但纵向 0，且 15-input 先判按钮，点键绝不会顺手推摇杆（预览页把两个数都打出来了，`最坏纵向重叠 = 0` 是硬指标） |
| c | 地表**只加密网格、不换算法** | 结构与生成流一个字没动 ⇒ **世界指纹仍是 `e9802f11`**（自检、TS 侧、游戏内三处一致），代价是 `tileCountPerChunk()` 变成"只能给渲染用"的接口（注释里已写明），以及地表层多花约 24 次落笔/帧 |
| d | 同档色**逐行攒路径**（一行一段 `rect`）而不是"每块一次 `fillRect`" | 256 块各自落笔就是 256 次/chunk × 可见 chunk 数，预算当场爆。攒路径后每 chunk 只 7 次（底色 + 5 档 + 细纹）：网格密 10 倍，地表层只从 38 涨到 62 |

## #16 阶段 A8 落地记录（2026-09-30：用户标准「一屏 128×128 格」+ 远距省笔档）

**起因**：用户先问"世界地图在玩家视角瓦片是多少×多少"（当时答：横向固定 **28.125 格**、
竖向随长宽比 39~62.5 格，19.5:9 手机典型 **28×61 格**；一格 ≈ 13.3 CSS px），随后给出新标准：
**改成 128×128 格**。

**歧义先摊开，再让用户选**：这句话有三种落法，我把代价列全再问，用户明确选了 B：
- **A**：整张世界地图 = 128×128 格（4096×4096 世界单位 = 8×8 chunk）——语义是"无限地图 → 有限地图"，产品级改动。
- **B（实际采用）**：**玩家一屏要塞下 128×128 格**（`cameraZoom` → 0.176）。用户明确"已知不可玩仍要做"。
- **C**：每 chunk 地表网格 16×16 → 128×128（`tileSize` 32→4，屏上一格 1.7 CSS px，纯噪点）。

**为什么最终落成"横向 128 格"**：竖屏一屏是长方形，**几何上不可能**同时塞下 128×128 个正方形格子；
标准只能钉在短边（横向）上。实测（`tools\view-metrics.mjs`，真跑 `SCREEN.resize` + `RENDER.viewRect`）：

| 设备 | 世界视野（世界单位） | 一屏格数 |
|---|---|---|
| 16:9 360×640 | 4096 × 7281.8 | **128.00 × 227.56** |
| 19.5:9 375×812 | 4096 × 8869.2 | **128.00 × 277.16** |
| 20:9 393×873 | 4096 × 9098.7 | **128.00 × 284.34** |
| iPad 768×1024 | 4096 × 5461.3 | **128.00 × 170.67** |

`cameraZoom = 720 / (128 × 32) = 0.17578125` → 横向**正好** 128 格；两个方向都 ≥ 128 格成立。
代价：一格 ≈ **2.9 CSS px**（原 13.3），角色（`player.radius = 24`）≈ **4.4 CSS px** —— 属"战略视角"。

**改动**：
- `shared/balance.json`：`view.cameraZoom` **0.8 → 0.17578125**；新增 **`view.lodZoom = 0.5`**，
  两处注释都写清"代价 + 回退方式"（改回 0.8 一个数就回到 A6 观感，省笔档自动关掉）。
- `16-render.js`：新增**纯函数** `groundDetailAt(k)`（只看传入倍率 → 自检可直接断言两个档位）+
  `drawGround` / `drawDecor` 的省笔档：低于 `lodZoom` 时地表只铺每 chunk 的底色一块
  （颜色与全细节档的第 0 档**逐位相同**）、装饰整层跳过。
- `19-selftest.js`：**旧的 `between('视角倍率在 0.5~1（拉远看得更多，又不会小到看不清）')` 这条设计下限
  被用户显式作废**（标准变了，防线也要跟着换），替换为新标准本身 + 省笔档的账，共 **+10 条**：
  横向正好 128 格（±0.05）、`视野宽 = 128 × tileSize`、竖向必然更长、两个档位判定、
  「省笔档只落底色 fillRect」、「关掉省笔档后重新建色档路径」、「省笔档下装饰整层跳过」、「阈值复位」。
  **608 → 618 条，全绿**。新增的 `countGroundFills()` 只数 `fill` / `fillRect`（省笔档的差别正好就在这两个数上）。
- 文档：`01-game-design` §19 + §16 的口径指针、`02-architecture` §9（预算表 + 历史表 + 叙事）、
  `03-roadmap` 阶段 A、`douyin-minigame\README.md`。

**为什么省笔档是"必须"而不是"顺手优化"**：不省的话视野里的 chunk 从 ~15 涨到 ~162，

## #17 阶段 A9 落地记录（2026-09-30：远距宏观档 + 演员层最小观感尺寸）

**起因**：A8 落地后用户看着 128 格的画面提了两件事 —— "视角的格子变多了，那你地图的刻画要更加细节呀，还有人物的大小"。

**先定标准："更细节"在这个尺度上是什么意思**（整条改动的判断依据）：一屏 128 格时一格只有 ~2.9 CSS px，
**"把细节画得更细"这条路已经走到头**（16×16 色档、每 chunk 40 道细纹、一件一件的装饰全是亚像素噪点）。
所以 A9 换的是**细节的层级**：把同一份东西放到**更大的尺度**上重画一遍，让"这里是什么地"看得出来。

**要 1：远距档从"省笔"升级成"宏观地图"（仍用 `view.lodZoom = 0.5` 那一档）**

- **地表**：同一份地表哈希（`TERRAIN.groundVariant`）**粗抽样**成 `view.lodGroundBlocks = 4` × 4 张色格
  （一格 128 世界单位 ≈ **11.7 CSS px**），6 档色照旧 —— **远看与近看是同一片地，只是抽样更粗**。
  粗色格的亮暗差比近景略大（`MACRO_SHADE = 0.09` vs 近景 0.07）：11.7 px 的格子要靠它才看得出纹理。
- **落笔**：粗色格按**同 band（= 同主题同色偏）的调色板槽**攒路径，每槽每档一次 `fill` ——
  一整屏 171 个 chunk 的地表落笔 **89 次**（比"每 chunk 一次 fillRect"还少），
  硬不变量是"落笔 ≤ 槽数 ×（6 档地表 + 3 种斑）"（自检里就断言这一条）。
- **装饰 → 宏观斑**：新增纯函数 `TERRAIN.decorBlobs(seed, cx, cy, band, maxBlobs)`，它按 `buildChunkDecor`
  **完全相同的调用顺序**跑同一条随机流（只是不建对象、只累加），按种类算质心与散布，返回
  ≤ `view.lodDecorBlobs = 2` 个斑（草甸 / 石滩 / 林地，半径 48~150 世界单位）。
  **"远看那片林子"就是"走过去看到的那片林子"的粗抽样**，不是另画一套示意 —— 自检直接断言
  "最大那个斑的种类 = 真实装饰里最多的那种，且质心逐位对得上"。斑按（槽 × 种类）攒路径，一整屏只花几次 fill。
- **缓存**：chunk 级宏观斑缓存（每个 chunk 只跑一次装饰流；键是整数，每帧 139 次查找不产生字符串）。

**要 2：演员层最小观感尺寸（新增 `view.actorMinZoom = 0.8`）**

- `RENDER.actorScale() = actorMinZoom / zoom`（低于 1 或不生效时为 1）；`beginActor(ctx, point, scale)`
  绕**角色自己的位置**反向放大 —— "画大"而不是"挪位置"，坐标公式一个字不改。
- **只放大点状的东西**：角色 / 怪的身体与影子、仇恨圈、精英圈与王冠、目标环、弹道、近战刀光。
- **面状的一律不动**（世界尺寸）：地表 / 路 / 营地 / 地标 / 技能 AoE 环（`ring` / `mend` / `bolt`）——
  放大它们就等于显示一个"假的攻击范围"。
- **文字与血条仍是设计像素**（字号不跟着放大 4.55 倍），但**抬升量跟着放大**，否则名牌 / 血条会被
  放大后的身体盖住。**攻击范围环在宏观档直接不画**：它按世界比例只剩 ~8 CSS px，会被身体整个盖住。
- 效果：角色在 375 宽的屏上 **4.39 → 20.00 CSS px**（= A6 时代的大小），一格仍是 2.93 CSS px。
- **代价（有意接受）**：世界被压缩 4.55 倍而角色没有 —— "角色看起来比脚下的地大"，贴身战斗时
  怪与玩家在画面上会重叠。一个数回退：`actorMinZoom = 0`。

**自检 +23 条（618 → 641，全绿）**：`decorBlobs` 9 条（个数上限 / 确定性 / 半径区间 / 件数不超过真实装饰 /
主种类一致 / 质心逐位一致）· 宏观档 5 条（落笔比 chunk 数少、落笔上限 = 槽 × 9、槽数上限、
整屏至少一半 chunk 有斑、`lodDecorBlobs = 0` 一个斑都不画）· 演员层 5 条（放大倍数 = actorMinZoom / zoom、
屏幕半径 = 世界半径 × actorMinZoom、观感尺寸 ≥ 18 设计 px、视角回到 actorMinZoom 时不生效、
`actorMinZoom = 0` 回退）+ **两条 save / restore 配平**（玩家与怪画完，画布变换深度必须回到 0 ——
防的正是"演员层缩放漏给 HUD"这种画面错位）。旧的"省笔档只落底色 fillRect"断言按新语义重写。

**尺子**：`tools\view-metrics.mjs` 现在同时打"粗色格 / 装饰斑 / 角色（含演员层）各几 CSS px"，
以及一张**宏观地形文本预览**（每字符 = 一个粗色格；0..5 = 色档、g / r / T = 草甸 / 石滩 / 林地）——
不跑 IDE 也能看出"地表有没有结构"（一片纯色 = 宏观档没生效）。

**账（`tools\perf-frame.mjs`，预算 900 落笔/帧）**：最坏 **545 → 450**；营地那一帧

**建路径 2150 → 5063**：粗色格真的建了路径 —— 这是"地表有纹理"的代价（落笔数反而更低）。
逐场景 545 → 450 / 527 → 414 / 536 → 423 / 462 → 396。

## #19 阶段 A11 落地记录（2026-09-30：地图与相机视角 —— 三个档位 / 相机前瞻 / 玩家标记）

**需求来源**：用户一句话 ——"地图，相机视角还需要优化，需要让地图更加细节，玩家视角更加清晰"。

**判断依据（这一版最值钱的一句话）**：细节与视野是**乘法关系** ——
`一格在屏幕上几 CSS px = world.tileSize × zoom × (cssW / designWidth)`。A8 的「一屏 128 格」让一格只剩
**2.93 CSS px**：在这个尺度上"把地画得更细"物理上不可见（A9 的宏观档已经是那条路的尽头）。
所以这一版不再硬抠一个数，而是**把选择交给玩家 + 把代价写在提示里**，另加三处"不用牺牲视野"的清晰化。

**① 三个视角档位（`view.cameraTiers`，默认中档）**

| 档 | 一屏横向 | zoom | 一格 CSS px | 地表 | 装载环 |
|---|---|---|---|---|---|
| 远 | 128 格 | 0.176 | 2.93 | 宏观 4 格一色格（11.7 CSS px） | 1 |
| **中（默认）** | **64 格** | **0.352** | **5.86** | **宏观逐格采样（5.9 CSS px）** | **2** |
| 近 | 32 格 | 0.703 | 11.72 | 逐格档（16×16 + 细纹 + 逐件装饰） | 2 |

- 每档的 zoom **由"一屏横向多少格"反推**（`designWidth / (tiles × tileSize)`，自检逐档验这条等式）：
  "一屏几格"只有一种算法，而且**远档就是 A8 的 128 格**（老标准没丢，只是不再是默认档）。
- **每档一个色格边长**（`lodBlockTiles`：远 4 格 / 中 1 格）：中档每 5.9 CSS px 换一次色、
  远档每 11.7 CSS px 换一次 —— 同一片地，**拉近一档 = 地表看得见的斑驳细一倍**。
- 切换入口：**设置面板一行「视角」**（点一下换下一档），写存档 `settings.zoomTier`（重开还记得），
  并 flash 一句带数字的提示；调试面板常显"视角 中（一屏 64 格 · 一格 5.86 CSS px · 宏观色格 1 格）"。
  > ⚠ 事后更正（见 #21）：**这一行当时并没有真的做出来** —— `handleAction` 里有 `zoomNext` 分支、
  > `setZoomTier` 也导出了，但 `18-panels.js` 的 menu 面板里没有任何一行产出这个 action（点不到）。
  > 玩家真正能改视角的入口是 #21 补上的**视角缩放滚动轴**（一屏 16 ~ 64 格）。

**② 让"细节"真的看得见（而不是更花）**

- **宏观调色板往主题主色收 45%**（`view.lodBlend`）：色格变小之后 6 档原色直接铺就是**噪声马赛克**；
  收一收 = "同一片地、淡淡斑驳"的纹理。
- **装饰斑三种都描轮廓**（原来只有林地描）：草甸 / 石滩 / 林地的边界看得出来 ——
  这是世界数据里**真实存在**的中等尺度结构（同一随机流聚合出来的，见 #17），不是画上去的假地形。
- **试过又退掉的**：地形等高线（把"结构色不同的相邻色格"描线）。数据不支持 ——
  `groundVariant` 是逐格哈希（白噪声），63% 的相邻格不同色，描出来不是等高线而是一张**噪声网格**
  （`tools\view-metrics.mjs` 的地形文本预览一眼看穿：满屏随机数字）。**教训**：先看数据的尺度，再决定画什么。

**③ 相机：前瞻 + 归位（"玩家视角更加清晰"的正面回答）**
> **更正（见 #22）**：这一条**已被后面的需求推翻**，下面这段保留为当时的记录 ——
> 前瞻让**远档**好看（240 单位只占半屏 5.9%），但**近距离视角下它会占半屏 34%~47%**，
> 把角色挤到屏幕边上。用户明确要求"视角没有锁定以角色为中心"，于是
> `view.cameraLookAhead` 240 → **0**（关掉）、`view.cameraLerpPerTick` 0.22 → **1**（每逻辑帧贴合）。

- `view.cameraLookAhead = 240` 世界单位（7.5 格）：镜头往"正在走的方向 / 正在打的目标"前移，
  屏幕正中变成"我 + 我要去的地方"（以前一半屏幕浪费在走过的路上）；停下来自己衰减回 0。
- **纯表现**：只改渲染用的相机，逻辑层读到的玩家坐标一个字节都没变（自检断言这一条）。
- `snapCamera()`：传送（公会 / 营地）、复活、读档、换档都归位 —— 否则镜头会带着上一处的前瞻"飘"过去。

**④ 三处小东西**

**② 画法（`16-icons.js` 的 `glowRing` / `heroGlow`，规格全在 `view.iconGlow`）**

| 规格 | 值 | 一句话 |

| `enabled` | true | 总开关：关掉就退回"只有阶色描边"（自检两条断言验它） |

| `lineWidth` / `alpha` | 2 / 0.42 | 每层描边粗细 / 最内一层的不透明度 |
| `pulseMs` + `pulseAmp` | 1500 + 0.45 | 呼吸的周期与幅度（**三角波**，见下） |
| `spinMs` | 900 | 炫彩每过这么久换一格（层与层再错开一位 = 看着像在流动） |

**① 为什么撤格子（而不是把格子做大一点）**

| 旧版面 | 问题 |
|---|---|
| 四列箱子格 × `gridRows` 排 = 12 格 | 背包上限 **200** 口，格子永远只列得下前 12 个（标题里得写"只列出前 12 个"）；开了 200 口与开了 12 口，面板长得一样 |

**② 三条纪律**

1. **恒六行**：袋子空了也是六行（数量 0 的那几行压淡写 × 0）—— "还缺哪一阶"一眼看得出来，

2. **清单只读**：开箱仍然只走上面那两个大按钮。旧的格子能点（`openChest count 1`），但它开的是

3. **没货不发光（A12 的纪律照旧）**：每行左边那口小箱走同一个 `iconBox` → `frame(..., phase)`，
   "这一阶 0 口箱"的那一行标 `dim`、只描阶色不发光 —— 自检用"六阶都有货比只有一口箱多出五行的光"钉死。

## #25 阶段 A14 落地记录（2026-10-01：**宝箱按阶开箱 + 按阶自动开启**）

|---|---|

| "要做按阶开箱得给开箱链加 tier 参数，那是玩法改动" | 加了，但**只在 20-main 内部**：`openChestAt` 把 A7 修订 2 的"先出装备、再扣箱"收成一处，`openOneChest`（第一口）与按阶开箱共用它 —— 旧的 `openChest count` 接口与口径一个字没改 |

**② 自动开启的三条纪律**

1. **一阶一枚、默认全关**：勾选表 `settings.chestAuto`（长度 = 阶数；`defaultSettings` 直接调
   `LOOT.defaultAutoFlags()`，两边永远同一份）。老存档没有这个字段 / 坏值 / 长度对不上 →
   `LOOT.autoEnabled` 一律当**关** —— 宁可不开，也别替玩家把箱子花掉。**升级后行为与 A13 一模一样**；
2. **不进背包**：`autoOpenChest` 不经过 `SAVE.pushChest`，于是不吃 `bagCap`、也碰不到"背包满了自动分解"；
   出装备走同一条 `rollEquipmentTier` + `grantEquipment`（A14 从 `openOneChest` 里**原样抽出来**的入账规则），

3. **报一句、不喊音效**：屏幕中央报"自动开出 …"（不报的话玩家会觉得"箱子怎么没了"），
   但**不播开箱音效**（挂机一晚几百箱，每箱咔一声就是噪音）。

## #26 阶段 A15 落地记录（2026-10-01：**背包分页 + 商城的强化石 + 营地铁匠强化**）

**① 强化等级存在哪里（这一条决定存档结构，先锁死再写代码）**

|---|---|

| 存部位（`save.enhance.weapon`） | 换装备时等级会"继承"给新件（玩家会拿 +10 的垃圾去换神装），而且四个部位要写进存档结构 |
| 只存武器 | 用户说的是"装备强化"，四个部位都该能强 |

## #27 阶段 A16 落地记录（2026-10-01：**公会自己输入名字 + 公会人员 / 等级 / 信息 + 左侧边栏**）

**需求来源**：用户三句话 —— "创建公会需要自己输入公会名"、"公会页面显示公会人员，公会等级，公会信息"、
"回到营地按钮设置在左边侧边栏，商城下面"；另加一句流程要求："全都做好之后直接搭建好后端到抖音云，由我来测试"。

**一句话结论**：公会的**规则与权威搬到了服务端**（`/api/guild/create|join|leave|anchor|mine|list` 六个端点，
`douyin-cloud\svr\index.js`）；客户端 `11-save.js` 新增 `G.GUILD`（名字校验 / 等级公式 / 记录归一化 / 服务端镜像），
`20-main.js` 新增一整段"公会的网络那一半"（建 / 加 / 退 / 同步 / 列表 / 自动刷新），`18-panels.js` 的公会面板
按"没有公会 → 输入名建会 / 加入"与"有公会 → 等级 + 信息 + 人员表"重排；HUD 左边缘新增**竖排侧边栏**
（上「商」下「营」），「商」从底部功能栏搬过去，`view.panel.leftReserve` 给卡片让出这条栏的宽度。

**① 三条必须先锁死的事（先定再写代码）**

| 事 | 结论 |
|---|---|
| **公会等级怎么算** | `level = 1 + floor(Σ成员等级 / 100)`，封顶 10。**用成员等级之和而不是另立一套公会经验**：服务端本来就存着每个账号的存档（`saves` 表里有 `level`），于是"公会多强"是现成的、**不需要任何新的上报接口**、客户端也伪造不了。客户端 `G.GUILD.levelFrom` 用同一道式子（断网时本机也能显示） |
| **"在线"怎么判断** | 没有长连接（决策 #2 仍未验证），所以是**"最近 2 分钟跟服务端说过话"**：`presence` 表在 `resolveIdentity` 里盖时间戳（每个带身份的请求都盖），超过 `balance.guild.onlineWindowMs` 算离线。面板每 15 秒自动刷新一次，玩家也可以手点 —— 口径如实写在界面与文档里，不假装"实时在线" |
| **连不上云时怎么办** | **单机永远能玩**（决策 #10）：建会在本机成立（`remote:false`），号角照扣（它是"建会资格"不是"服务端登记费"）；下次能连上时 `/api/guild/mine` 回 `inGuild:false` 而本机有会 → 自动拿**同一个名字**补登记一次（不重复扣号角）。名字被别人抢了才失败，那时界面写明"本机这份留着"（**绝不静默删玩家的公会**）。这条自愈同时覆盖"服务端重启把内存里的公会弄丢" |

**② 名字：公会名与昵称同一套规则**：2~12 字、中文 / 字母 / 数字 / 下划线、保留名不给用 ——
客户端 `G.GUILD.validate` 直接**借** `G.ACCOUNT.validate`（连"先看非法字符再看长度"的顺序一起继承），
只放掉一条"本机昵称注册表"：那管的是"这台设备上没人用过"，而公会名的唯一性是**全服**的，
只有服务端说了算（`409 name_taken`）。两处各有一份实现，与昵称规则一样是**故意的**：
客户端那份管手感（打字时立刻看到能不能用），服务端那份管权威（改了客户端也骗不到一个重名）。
**"自己输入"走平台键盘**（`tt.showKeyboard`，与登录页的昵称输入同一条路）；模拟器里没有这个 API，
所以「随机取一个名字」那一行留着当兜底 —— 那台机器上"建会"这条路不能断。
